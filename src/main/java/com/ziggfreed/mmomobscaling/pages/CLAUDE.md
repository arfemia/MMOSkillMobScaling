# pages/ - in-game admin config UI

Router for `com.ziggfreed.mmomobscaling.pages`. The mod's ONLY interactive UI page (the HUD overlays live in `hud/`). Opened by `/mobscaling ui` (admin-gated at the command); do not add another entry point.

- **[`MobScalingAdminPage`](MobScalingAdminPage.java)** extends the engine `InteractiveCustomUIPage<EventData>`. SPEC-DRIVEN: five `ziggfreed-common` `ui/form.SettingsForm` instances (Global, Zone HUD, Inspector HUD, a per-world editor, and a zone/biome FLOOR editor), each rendered from an ordered `FieldSpec` list (`buildGlobalSpecs()` / `buildZoneSpecs()` / `buildInspectorSpecs()` / `buildWorldSpecs()` / `buildFloorSpecs()`) - every CONSUMED knob across the settings schema is editable in-game, every per-world leaf `WorldSettings` decodes is exposed on the per-world form (the two HUD groups in full, `OpenWorld.RegionSizeChunks`, and all THREE `Where` axes - `Match`, `GameplayConfig`, `ExcludeMatch` - as comma-separated CSV fields, so an instance world is targetable by its config key), and every leaf of a `Difficulty/*.json` mapping is exposed on the floor form. Worlds and Floors are TWO-PANEL layouts (`.ui`: `Common/UI/Custom/Pages/MmoscalingAdminPage.ui`) - a scrolling list on the left, the add/edit editor on the right; both lists append the MOD-LOCAL `Pages/MmoscalingWorldRow.ui` (NOT the common `Pages/ZigListRow.ui` - see the world-row bullet below), per-knob rows append the common `Pages/ZigForm*Row.ui` templates (the NOTE template wraps multi-line). The tabs are a `Tab` record list (`TABS`: id, button, section, label key); `buildTabs` labels + binds them and `applyTabState` tints the active one and shows exactly its section, on build and on every switch.
- **[`ScalingPreview`](ScalingPreview.java)** is the preview column's arithmetic, pure and engine-free (its own `ScalingPreviewTest`): `sample(curve, d)` is the fold's own `MobScaleFold.plain` result read back with the time to kill (`hp / in`) and the two rail flags asked of the curve (`DifficultyStatCurve.effectiveHpRailed` / `outRailed`), and `ladder(curve, clamps, rarities, d)` folds the plain mob then every tier weakest to strongest through the real `MobScaleFold.fold` (no variant, no affixes) at the fold's own `curveDifficulty`. The page never computes a factor itself.
- **[`RoleBaseHealthResolver`](RoleBaseHealthResolver.java)** and **[`RoleBaseHitResolver`](RoleBaseHitResolver.java)** supply the sample role's real base numbers (see the baseline bullet below); both are display-only and never gate gameplay.

## Hard rules (do NOT regress)

- **A knob nothing consumes is DELETED from the schema, never parked off the UI.** Every `FieldSpec` on every form writes a leaf some gameplay or HUD path reads; a leaf that stops being read leaves the codec, the fold, the page and the lang files together (an owner file still carrying it stays valid, since `BuilderCodec` skips an unknown key). Do NOT add a spec for a leaf without a consumer, and do NOT keep a consumer-less leaf in the codec "for an owner who still sets it by hand". The 1.2.1 audit (settings leaf by leaf against the five spec tables) found exactly two consumed leaves with no control, `Where.GameplayConfig` and `Where.ExcludeMatch`, and exposed them; the settings asset's `Name` echo is deliberately not a knob (its setter is a no-op, the filename is the id).
- **Adding a knob is ONE spec line + ONE lang key, never a new `.ui` row.** A `FieldSpec` (id, kind, leaf path, label key, optional dropdown values) appended to the matching `buildXSpecs()` list is the whole surface change; the shared engine renders/binds/collects it. Do NOT hand-write a `.ui` row or a per-field codec key for a new knob - that regresses back to the pre-1.0.2 shape this rework replaced.
- **Global tab order is difficulty-first (round-2 hardening).** `buildGlobalSpecs()` runs `enabled` note -> Difficulty (floor/caps) -> the stat Curve (`ehpPerPoint` leads it: the one tank slope, then `hpShare`, `outScale`, `outShape`, `maxEhp`, `maxOut`) -> the safety Clamps (`minHp`/`maxIn`/`minOut`/`minLoot`/`maxLoot`) -> rarity + distance escalation (`rarity` leads it) -> Open World last. The curve and clamp specs are appended by `addCurveSpecs`/`addClampSpecs`, once with no prefix for the Global form and once with the `w` prefix for the per-world form (`fieldId`), so the two tables cannot drift. Preserve this order when adding a new global knob; drop it into the group it semantically belongs to, not the end of the list.
- **Every leaf-bearing/toggle `FieldSpec` (all five forms) carries a `.withHint(lang-key)`, and a hint says what the number does IN GAME, never restates the field name.** `ui/form.FieldSpec.withHint`/`SettingsForm.applyHint` render a `#Hint` sub-label under the row; `HEADER`/`NOTE` specs cannot carry one (`withHint` throws). A NEW knob's hint is ONE qualitative sentence (no digits restating balance defaults) at `mmomobscaling.ui.hint.<id-ish>`. A world-form field that reuses a GLOBAL label key verbatim (identical meaning, just a per-world override - most plain NUMBER/DROPDOWN leaves) REUSES that global hint key too; a TRISTATE, a pool gate, or a world-identity field (id/selector/parent) has no true global equivalent (Inherit is a distinct affordance from a plain toggle) and gets its own `w_*`/`pool_*`/`world_*` key - see `buildWorldSpecs()`'s doc comment for the exact rule. The floor form's four fields carry `floor_*` hints of their own.
- **Both CRUD editors show what a blank/Inherit field currently resolves to.** `refreshWorldHints` (called from `handleEditWorld`/`handleSaveWorld`/`handleClearWorld`) and `refreshFloorHints` (its floor twin) compose the spec's static hint with a computed "Inherits: {value}" line (`mmomobscaling.ui.world.inherits`) via `Message.join(staticHint, Message.raw("\n"), inheritsMsg)` for every field still blank/Inherit; an authored field shows the static hint alone. The inherits segment renders WHITE + BOLD end to end (`inheritsSegment`: `.color`/`.bold` on BOTH the frame message and the nested `value` param - a span does not inherit its parent's styling, so both need the call). A world field's effective value is `WorldSettingsConfig.effectiveById` (the `Parent`-merged view) falling back to the GLOBAL live `MobScalingConfig` value per leaf (`effectiveWorldDisplayValues`) - a Pool gate's global is allow-all / an empty deny list / neutral scale / zero extra slots; a per-world HUD tri-state's global is the zone/inspector enabled flag; the three `Where` fields have no global to inherit and get static hints only. A floor field's inherited value is the SHIPPED mapping of that id (`DifficultyConfig.packMapping`, the layer an owner file overlays): the localized type word, the literal target name, or the floor bound as a TYPED number through the bare `mmomobscaling.ui.number` frame (`inheritedFloorLeaf`). A blank id (a cleared/new editor) always shows static-only - there is nothing yet to resolve.
- **The Global tab is two-panel: settings left, a SCROLLING preview column right, and that column is the ONE place a consequence is shown.** No per-field computed row exists and none may be added; a new derived readout goes on this column. Top to bottom (`buildPreviewPanel` at build, `refreshPreview` on every Global-form `field`/`press`/`saveGlobal`/`selectPreset` event via a PREVIEW-ONLY partial update that never re-pushes the form's own values): (1) `#MmoscalingPreviewList`, five appended `Pages/MmoscalingPreviewRow.ui` rows, a PLAIN Skeleton at five evenly-spaced difficulties between the CURRENT MinCap/MaxCap; (2) the MANUAL PROBE ("Try a difficulty", `mmomobscaling.ui.global.preview_custom`, a hand-bound TextField with its own `"previewD"` action - it lives OUTSIDE the SettingsForm, there is no leaf to persist) driving ONE more row in `#MmoscalingProbeList`, shown only while the field parses to a difficulty `>= 1`, deliberately UNCLAMPED to the Min/Max band; (3) the RARITY LADDER (`#MmoscalingLadderTitle`/`Note`/`List`): the plain mob then every folded tier weakest to strongest (`RarityConfig.all()`, so a pack's tier takes its place), each read at the probed difficulty times its `DifficultyMultiplier` (the baseline `floor` field's value while nothing is typed), rows cleared + re-appended on every refresh since a preview row carries no button; (4) the read-only MMO panel (next bullet). Every figure comes from `ScalingPreview` over a curve and clamps built through the public `MobScalingConfig.buildCurve` / `buildClamps` from the form's values (`previewValue`: blank/invalid falls back to the live getter, mirroring `collectLeaves`'s NUMBER rule but degrading instead of blocking - read-only, never a persist), the same constructors the fold and the per-world overlay use, so the preview can never disagree with a Save. A preview row is TWO wrapping lines: `#Line` = `D{diff}   HP {hp}   Hit {out}   Taken {in}%` (a ladder row leads with the tier's name in its own colour and its multiplier), `#Detail` = `Kill time x{ttk}` (`hp / in`, how many times longer than an unscaled mob, the number the curve is derived to hold) plus an amber `preview_rail_hp|out|both` marker joined at the top level when `MaxEffectiveHpMult` / `MaxOutDamageMult` is what decided the row (a railed row is where turning a slope up changes nothing). Every number is a TYPED param (`oneDecimal` / `twoDecimals` doubles, `Math.round` longs), never a server-formatted string; a multiplier cell is the nested `preview_mult` / `preview_mult_abs` frame (`x2.56` / `x2.56 (179)`). **Precision rule: a factor shown beside its own product carries two decimals, everything else one.** A multiplier (a rung's `DifficultyMultiplier`, a cell's HP/Hit factor) is `twoDecimals` because the number next to it is its product (the rung's D, the cell's absolute) and an admin multiplies through by hand: at one decimal Rare's authored 1.35 read `x1.4` beside `D41`, and 30 x 1.4 is 42. The ladder title's difficulty and a rung's D are `oneDecimal` (the exact curve read, so a title of 30 at `x1.35` shows `D40.5`, never a whole-rounded `D41`); the five sample rows' D stays `Math.round` (nothing multiplies through a sample), as do `Taken {in}%` and the absolutes, and kill time stays `oneDecimal` (a ratio read as a magnitude).
- **The HP and Hit cells show the Skeleton's REAL base numbers, each from its own resolver, observed preferred.** HEALTH: `RoleBaseHealthResolver`, TWO sources. (1) OBSERVED ground truth: `MobScalingRollSystem.recordObservedBaseHealth` feeds it each spawning mob's Health-stat max read BEFORE this mod's own `mmoscaling_hp` modifier applies - and SKIPS the reading when that modifier is ALREADY present (a RELOADED already-scaled mob still carries the persisted modifier by the time the roll runs, so its max is post-scale, not base; fresh spawns supply the true value). (2) TEMPLATE read, entity-free: `NPCPlugin.getIndex(String)` -> `getRoleBuilderInfo(int)` -> `BuilderInfo.getBuilder()` off the loaded-asset registry; a PLAIN `BuilderRole` evaluates its `maxHealth` holder directly, a `BuilderRoleVariant` (the vanilla Skeleton: `"Type":"Variant"` + `"Reference"` + `"Modify"`) mirrors the engine's own `BuilderManager.validateAllSpawnableNPCs` evaluation (seed an `ExecutionContext` from the variant's parameters, fold the `Modify` chain via the PUBLIC `createModifierScope`, walk `getReferenceIndex()` to the TERMINAL template, evaluate ITS holder against the folded scope, always via `rawGet(ctx)` since a `Compute` holder NPEs on the static shortcut). The ONE non-public hop is `BuilderRole`'s `protected final IntHolder maxHealth` field - one cached reflective `Field`, permanent failure flag, fully `try/catch(Throwable)`-guarded and memoized per role (observed readings still land later). HIT: `RoleBaseHitResolver`, OBSERVED ONLY, and deliberately so: a role's hit is not a role field, it lives in whichever attack chain fires (the held weapon's own interaction for an armed mob - the Skeleton draws a random weapon from a loadout - and the role's `InteractionVars.Melee_Damage` calculator only for an unarmed one, which the shared source itself marks "not applicable" once a weapon overrides it), there is no public entity-free accessor for it, and a template read of the role's own calculator would be wrong for exactly the mobs an owner previews. `MobScalingDamageFilter.observeBaseHit` feeds it the hit a scaled attacker dealt as the engine rolled it (before this mod's multiply and before armor), per role via `EntityIdentifierUtil.roleName`; last write wins, so the cell reads "the last hit a Skeleton landed" (the preview note says so). Either base absent = that cell shows the multiplier alone.
- **The MMO panel is READ-ONLY and every read is guarded.** `buildMmoPanel` (build) paints the power floor and ceiling this mod can see through the frozen `MMOSkillTreeAPI` (`getPowerLevelMin/Max`, via `config/MmoPowerBounds`, the same guarded read the boot audit's caps cross-check uses) or one `ui.mmo.unavailable` line when a missing/older MMO jar answers nothing, the viewing admin's own power (`MmoPowerBounds.of(store, ref)`, read once at build where the store is in hand), and the static `ui.mmo.where` line naming where those numbers are edited (the MMO's Power Level admin page / `mods/mmoskilltree/power-level.json`, and `ability-clamps.json` over `Server/MMOSkillTree/ModifierClamps` for the mitigation ceilings this mod cannot read). `refreshMmoCapLine` (every preview refresh) says how the form's CURRENT MinCap/MaxCap sit against those bounds (`cap_above` is the supported way to let far zones out-scale a maxed group, `cap_below` folds every strong group onto one difficulty, plus a `floor_mismatch` line), the same comparison `ScalingContentValidator.validateDifficultyCaps` makes at boot. This mod never widens that API and never writes an MMO file from here.
- **World rows wrap: `Pages/MmoscalingWorldRow.ui` is a MOD-LOCAL template, not common's `Pages/ZigListRow.ui`, and the Floors list reuses it.** Modeled on the shared row (same child ids: `#Title`/`#Sub`/`#Badge`/`#EditBtn`/`#RemoveBtn`, `$Z.@ZigRichRowBtnStyle` kept on the buttons for click sounds) but sized for this page's 300px list panel: `#Title` WRAPS (`Wrap: true`, no fixed height) so a long world id / match pattern shows two lines instead of truncating, `#Sub` WRAPS too (a floor row's sub line outgrows the text column once the Remove button is showing, and a floor id is short enough to leave the 64px row the height for two sub lines), the row itself carries the fixed `Height: 64`, and `#Badge`/`#EditBtn`/`#RemoveBtn` are narrower to leave room. `buildWorldList` and `buildFloorList` (Java) share the template-path constant (`ROW`); a world row's `#Sub` is a literal DATA summary on `.Text` (`worldSummary`), a floor row's is the localized `ui.floor.row_sub` frame on `.TextSpans` (type word, literal target, typed floor). A floor row's `#Title` is `DifficultyMapping.id()`, which is a DISPLAY name: `DifficultyOwnerLayer.overlay` gives an owner file overlaying a shipped mapping the SHIPPED id's authored spelling (`Zone2`), never the lower-cased file key it is resolved by (`zone2`), so the title does not case-flip the moment an owner overrides it; only a mapping nothing ships under is titled by its file key.
- **`EventData` is exactly five keys: `Action`/`Tab`/`Id`/`Field`/`@Value`.** Every `SettingsForm` row speaks this shape (`Action="field"` + `Field`/`@Value` on a value change, `Action="press"` + `Field` on a toggle click); a hand-bound control (the preset dropdown, the probe field) must emit the SAME shape, never a bespoke key. `Id` is the row id of whichever list a button sits in (a world file id for `editWorld`/`removeWorld`, a floor mapping id for `editFloor`/`removeFloor`). Do NOT add a per-field codec entry back onto `EventData` - that is exactly the 24-key shape this rework collapsed.
- **NEVER reopen the page.** `handleDataEvent` never calls `openCustomPage`/a page rebuild; every branch answers with a PARTIAL `sendUpdate(cmd[, events], false)` (a full `openCustomPage` resets scroll position - the bug this rework fixed). A `"field"` action is cache-only for Zone/Inspector/World/Floor (`SettingsForm.cache`, no packet at all); a GLOBAL field additionally answers with a small PREVIEW-ONLY partial update (the preview column, never the form's own values - see the preview bullet above); a list change (save/remove) clears + re-appends + rebinds the list rows in the SAME update - the official shared-source `ChangeModelPage.buildModelList` pattern (`hytale-shared-source/HytaleServer/builtin/Model/.../ChangeModelPage.java`): `cmd.clear(sel)`, re-append rows, rebind their buttons, `sendUpdate(cmd, events, false)`.
- **Every edit persists through ONE path: `config/MobScalingOwnerWriter`** (-> the common `JsonOverrideWriter` -> the owner file `mods/MmoMobScaling/mob-scaling.json` -> `MobScalingConfig.refreshFromDisk`; the same class owns the per-world file writes and the zone/biome floor writes under `mods/MmoMobScaling/difficulty/`, which the Floors tab drives through `saveDifficultyMapping`/`deleteDifficultyMapping`). The page NEVER writes a file itself and NEVER mutates `MobScalingConfig` fields directly. A `TOGGLE` spec is INSTANT-persist (never collected by `SettingsForm.collectLeaves`; the page's `handlePress` flips + saves + optionally live-applies on click, driven by a small `id -> ToggleDef` lookup table, not a chain of switch arms). Every other tab (`Global`/`Zone HUD`/`Inspector HUD`) is ONE Save button per tab: `collectLeaves(false)` (a blank NUMBER/INT is a validation ERROR on these three forms - nothing here is optional/inheritable) then `MobScalingOwnerWriter.saveLeaves(...)`. HUD + preset edits ALSO live-apply (`ZoneDifficultyHud`/`MobInspectorHud.setEnabledForAllOnline`/`refreshPositionForAllOnline`, `swapActivePreset`); after a tab save, the form RESEEDS from config + `applyValues` so fold-clamped values (e.g. `MaxCap >= MinCap`) reflect back into the UI. The SAME `MobScalingOwnerWriter` path backs the `/mobscaling` command, so the two never diverge.
- **`Enabled` needs a restart** (the zero-cost registration gate registers systems only at `setup()`): persist + flip the field but the UI shows the "takes effect on restart" note (`mmomobscaling.ui.status.saved_restart`, wired via the `enabled` toggle's `ToggleDef`). Never try to live-(un)register.
- **The per-world editor seeds from the AUTHORED body, NEVER the Parent-merged effective view** (`WorldSettingsConfig#authoredById`, NOT `foldedView()`/`effectiveById()` - those two are backed by the SAME already-Parent-merged map, so neither is safe to seed an editor from). With ~50 exposed per-world knobs, seeding the merged view and saving back would materialize every inherited leaf into the child file and silently break inheritance; `authoredById` decodes the file's own raw JSON (jar/pack/owner id-replace layering still applies, no `Parent`-chain walk), so a blank field / the Inherit tri-state round-trips as "inherit" instead. `collectLeaves(true)` (blank IS inherit, the only forms where this is true are the two CRUD editors) writes a NULL leaf for anything left blank/Inherit, so the saved file carries exactly the authored leaf set. The `worldId` spec's leaf path (`$Id`, the shared `ID_LEAF` sentinel) is popped from the collected map before every save - the filename IS the id, there is no `$Id` codec key. Save id = the World-id field, falling back to the first `Match` pattern, then the first `GameplayConfig` key (all run through `OwnerFiles.sanitizeFileId` - so does the self-`Parent` comparison, or a differently-spaced/cased id+Parent pair slips the check); when the id and both of those are blank the save is rejected (`id_or_match_required`); a blank selector with a non-blank id IS legal (a pool-only BASE file). The three `Where` fields are CSV specs, so each collects as the LIST leaf the codec wants and an empty one as a removal - no wrapping in `handleSaveWorld`, and no "first pattern only" caveat: a rule with several patterns round-trips whole. Remove = `deleteWorldFile` (a shipped same-id file re-folds). A self-`Parent` is rejected inline; deeper cycles warn at fold.
- **The floor editor seeds from the owner file's OWN leaves and overlays the shipped mapping per leaf.** `handleEditFloor` seeds from `DifficultyOwnerLayer.authoredById` (the owner file decoded through `DifficultyMappingAsset.CODEC`, nothing else), so a shipped mapping with no owner file yet seeds every field blank/Inherit and the hints say what each inherits; `handleSaveFloor` derives the id from the file-name field, else the zone/biome name (the `*` wildcard cannot name a file and needs one: `floor_id_required`), pops `$Id`, and writes the collected leaves through `MobScalingOwnerWriter.saveDifficultyMapping` - a file named after a SHIPPED mapping (`DifficultyConfig.packMapping(id) != null`) may carry only the leaves the admin authored (the README's `{"Floor": 12}` shape), a brand-new id is refused unless `TargetType`, `TargetId` and `Floor` are all set (`floor_incomplete`, the same rule the owner layer would only warn about at fold). The type dropdown's VALUES are `inherit` / `Zone` / `Biome` (the codec's two words, re-cased on seed through `DifficultyMapping.TargetType.parse` so a hand-cased file still shows its value); its LABELS are the localized `ui.floor.type_inherit` / `type_zone` / `type_biome` words, pushed once at build by `localizeFloorTypeEntries` as `DropdownEntryInfo(LocalizableString.fromMessageId(key), value)` entries over the row the shared form built (`SettingsForm` paints a DROPDOWN's entries as literal label == value pairs, and `applyValues` later touches `.Value` alone, so the relabel survives every partial update). Remove = `deleteDifficultyMapping`, whose boolean answer decides the status: true clears the editor, rebuilds the list and says `floor_deleted` (the shipped mapping stands again); false (no owner dir, no file under that id, a filesystem refusal) changes nothing on the page and says `floor_delete_failed`. Only an owner-authored id (`DifficultyOwnerLayer.ownerAuthoredIds`) shows the Remove button. The list is every FOLDED mapping (`DifficultyConfig.all()`), zones before biomes, wildcards last, then by target name (`FLOOR_ORDER`).
- **The two HUD groups and `OpenWorld.RegionSizeChunks` are per-world in FULL, and the world form exposes every leaf.** `wZoneHud`/`wZoneShowLoc`/`wZonePos`/`wZoneOffX`/`wZoneOffY`/`wZonePrefix`/`wBiomePrefix` under the `ui.world.zone_hud_header` header, `wInspHud`/`wInspPortrait`/`wInspPos`/`wInspOffX`/`wInspOffY`/`wInspRange` under `ui.world.inspector_hud_header`, and `wRegionSize` in the Open World group write the leaves `ResolvedWorldSettings` overlays per leaf. The HUDs read them for the world the viewing player stands in: the corner through `ScalingHud.worldSettings()` (at build and on the live reposition), the location line / name-key prefixes / inspector reach / portrait through the per-world view `MobScalingHudSystem` hands each push (the system leaves the snapshot's `modelRole` null when the world's portrait toggle is off, so the inspector card reads no config of its own). The per-world dropdowns lead with `inherit` (`POSITIONS_INHERIT`, like `AGGREGATION_MODES_INHERIT`); the tri-states carry their own `w_*` hints, the plain leaves reuse the global ones. **Every save that can move a HUD calls `refreshHuds()`** (a preset swap, a Zone/Inspector tab save, a world-file save or delete), which re-anchors each online HUD to ITS world's corner (`ZoneDifficultyHud`/`MobInspectorHud.refreshPositionForAllOnline()`, no position argument) rather than pushing one global corner to everyone. The two prefix fields are TEXT, and on the world form blank means inherit, so an explicitly EMPTY per-world prefix (prettify the raw id instead of looking a key up) is authored in the file, not the form - and it SURVIVES the form: `handleSaveWorld` runs the collected leaves through `WorldFormLeaves.keepAuthoredEmptyText` against the file's authored body (`authoredById`), which puts an authored empty string back where the form left a blank, so a Save of that world no longer removes the leaf and silently switches it to the inherited prefix (a blank over an authored NON-empty prefix still means inherit). `WorldFormLeaves` is a pure, engine-free helper with its own test.
- **Overriding a shipped/pack world for the first time is copy-then-edit, not replace-then-edit.** `MobScalingOwnerWriter.saveWorldFile` seeds the brand-new owner file from `WorldSettingsConfig#authoredRawJsonById` (a deep clone of the shipped body's raw JSON - its `Parent`, any `$Comment`, and every leaf, exposed by the UI or not) BEFORE merging the caller's collected leaves on top; editing an EXISTING owner file skips the seed (a plain partial merge, unchanged). Without the seed step a fresh override would carry ONLY the ~50 exposed knobs, silently dropping everything else the shipped body authored (a `$Comment`, a leaf the form has no row for, ...) - an owner file otherwise replaces the shipped body WHOLESALE by id (layering is id-replace; inheritance is `Parent`'s job). A blanked EXPOSED field still REMOVES that leaf from the copy (a null leaf persists as a removal exactly like it would against an existing file); an unexposed leaf is never touched. A floor file needs no such seed: it overlays the shipped mapping per leaf by contract, so a partial file is the intended shape.
- **A `collectLeaves` validation failure names the failing field**: `mmomobscaling.ui.status.invalid_field` with a `field` param = `Message.translation(errorLabelKey)` (a NESTED client-resolved `Message`, validated against the official `PortalDeviceActivePage` precedent - `.param(key, Message)` renders correctly on `.TextSpans`, not just chat). One generic key covers NUMBER/CHANCE/INT failures (its value text explains all three forms) rather than branching to kind-specific keys.
- **Namespace every id `#Mmoscaling*`** (the client UI namespace is flat + cross-mod). CRUD-row bare ids (`#Title`/`#EditBtn`) and preview-row bare ids (`#Line`/`#Detail`) are safe only because the indexed parent (`#MmoscalingWorldList[i]`, `#MmoscalingLadderList[i]`) scopes them; the SAME rule covers the appended `ui/form` rows (`#MmoscalingGlobalForm[i] #Field`, etc.).
- **The shared settings-UI toolkit is `ziggfreed-common`** (`ui/SettingsUiUtil`, `ui/ZigRichButton`, `ui/hud/HudPosition`, `util/JsonOverrideWriter`, `Pages/ZigListRow.ui`, and as of 1.0.2 `ui/form/` - `FieldSpec`/`SettingsForm` + the five `Pages/ZigForm*Row.ui` templates) - reuse it, do not re-derive a binding/row-rendering helper here. It has no READONLY kind on purpose: a computed readout is the preview column's bespoke pattern, not a `FieldSpec`.
- **The escalation-origin pair (`escOriginX`/`escOriginZ`, `wEscOriginX`/`wEscOriginZ`) is the ONE optional, possibly negative number on the Global tab, and it is TEXT for that reason.** The shared kinds cannot spell it: NUMBER rejects a minus sign, INT refuses to be blank under the Global tab's `collectLeaves(false)`, and neither has an "unset" spelling there. So both fields are `FieldSpec.text` on both forms and the pure `EscalationOriginLeaves.normalize` (its own test) turns the collected strings into the codec's `Double`/`null` leaves right after `collectLeaves` in `handleSaveGlobal` and `handleSaveWorld` (blank = the leaf removed, so the axis reads the world spawn point again; a non-number refuses the save with `ui.status.invalid_origin` naming the field through `labelForLeaf`). The Global form seeds them BLANK when unset (never a number standing in for the spawn point); the world hint's inherited value is the authored coordinate as a TYPED number or the localized `ui.world.inherits_spawn` phrase (`originDisplay`). Do not generalize this into a form-wide "blank is inherit" on the Global tab, and do not add a third TEXT-parsed number without a reason as strong as this one.
